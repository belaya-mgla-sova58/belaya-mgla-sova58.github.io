# «Белая мгла» — защита счётчиков

**Статус на 21.11.2026: подготовлено, НО НЕ РАЗВЁРНУТО.**
Этот каталог сам по себе **не защищает действующие** Abacus/Firebase-счётчики.
До развёртывания Cloudflare Worker, миграции значений и замены старого клиентского кода рабочие публичные счётчики остаются уязвимыми. Нельзя обещать пользователю обратное.

## Что подготовлено
- `worker/src/index.mjs`: Cloudflare Worker API с защищёнными GET/POST для просмотров и лайков.
- `worker/migrations/0001_counters.sql`: таблицы D1 для сумм, предотвращения повторов и лимитов запросов.
- `worker/wrangler.jsonc`: конфигурация Worker (вставить ID реальной базы).
- `site/secure-stats-v1.js`: **неактивный пока** адаптер сайта. Работает только при указанных `SOVA_SECURE_STATS.apiUrl` и `turnstileSiteKey`.
- `worker/test/smoke.test.mjs`: минимальные проверки API и ошибочных запросов.

## Как устроена защита
Каждый запрос изменения счётчика требует **отдельный токен Cloudflare Turnstile**, который проверяется **на сервере** (hostname + action).
Для просмотра действует окно 24 часа на один распознанный браузер, для лайка только одна запись на распознанного посетителя за всё время. Ограничение частоты: максимум 30 запросов в минуту на IP.
Worker хранит HMAC-хеши идентификаторов, а не IP в базе. `HASH_SECRET` должен оставаться только в Cloudflare Secrets.
Состояние может не совпадать между устройствами, с VPN/NAT и при очистке браузера. Это сильная защита от простой накрутки, но не гарантия «один реальный человек = один просмотр» против распределённых ботов.
CORS и проверка Origin не являются аутентификацией, поэтому все POST дополнительно проходят проверку Turnstile.

## Однократное развёртывание
Нужен доступ владельца к **Cloudflare**; этого доступа сейчас в чате нет. Не передавать секретные ключи через публичный GitHub или сообщения.

1. Создать/открыть аккаунт Cloudflare и новый Turnstile widget с hostname `belaya-mgla-sova58.github.io`. Записать site key (публичный) и **secret key** (закрытый).
2. В терминале в `security/worker` выполнить `npm install`, авторизовать `npx wrangler login` и создать D1 базу: `npx wrangler d1 create belaya-mgla-counters`.
3. Вставить полученный `database_id` в `worker/wrangler.jsonc` вместо `PUT_YOUR_D1_DATABASE_UUID_HERE`.
4. `npm run db:migrate:remote`, затем `npm run deploy`.
5. В Cloudflare для Worker добавить два **секрета**, не в GitHub: `HASH_SECRET` (длинное случайное значение, ≥32 байт) и `TURNSTILE_SECRET` (секретный ключ созданного widget). Через CLI: `npx wrangler secret put HASH_SECRET` и `npx wrangler secret put TURNSTILE_SECRET`.
6. Проверить `GET https://<имя>.workers.dev/v1/counts/ogonek-barash` (ожидается JSON с `views:0,likes:0`) и негативные запросы POST: без действительного Turnstile токена счёт не меняется.
7. **До включения** на сайте перенести в D1 проверенные текущие значения, включая лайки! Для этого отдельно читать живые старые значения Firebase/Abacus и однократно `INSERT ... ON CONFLICT` в `counters`. **Не переносить подозрительные исторические просмотры**, выбирать согласованные начальные значения. По состоянию на 21.11: ориентир для «Огонька» Бараш 73 + новые посещения, zimbabe 15 + новые посещения, WhiteFox №03 и №04 отсчитываются заново с этой даты; значения на момент переключения нужно перепроверить. У выпусков №05, №02 и других статей нельзя произвольно обнулять лайки.
8. Подключить `site/secure-stats-v1.js` к нужным страницам, выставить `window.SOVA_SECURE_STATS={apiUrl:'https://<имя>.workers.dev',turnstileSiteKey:'...'}`, добавить `data-secure-slug` и поля `data-secure-views`, `data-secure-like`, `data-secure-like-count`. На **самих статьях** добавить `data-secure-article`; на карточках списка его не ставить. **Убрать старые обработчики hit/PUT**, иначе они продолжат записывать в открытые базы параллельно.
9. Проверить на опубликованном сайте: 1 реальный просмотр, обновление страницы, другая вкладка, один лайк, повторный лайк, Turnstile error, мобильный браузер, мобильное приложение PWA, Яндекс.Метрика. Только затем полностью переключить остальные счётчики.
10. **После миграции всего функционала** сузить правила Firebase Realtime Database: закрыть прямые публичные изменения старых лайков и просмотров, при этом сохранить возможность работы комментариев и остальных функций. Делать это в консоли Firebase после отдельного аудита правил: грубое закрытие `/likes` сломает комментарии.
11. Наблюдать D1 и логи Worker, обновлять лимиты по данным о ложных отказах.
